# AML v1.1 Plan — From v1.0 to a usable product

Status legend: ⬜ not started · 🟨 in progress · ✅ done

## Definition of "usable product"

All points are measurable; all but the field gate are automated tests.

1. **No lost traffic on a clean chain:** both profiles decode 100 % across all start offsets and feed chunk sizes 64–4096 samples.
2. **No stuck notes:** 1000 random NoteOn/NoteOff pairs over a corrupted channel end with every note released (by its NoteOff or by All Notes Off).
3. **Bounded TX latency:** Fast profile queue latency < 250 ms at 10 msgs/s; heartbeat uses zero airtime while traffic flows.
4. **Fail-safe on every outage:** if the audio device stops delivering samples, All Notes Off is sent within `link_dead_ms` + 100 ms.
5. **Level tolerance:** decoding works from −30 dB to 0 dB relative to the transmit level.
6. **Honest latency:** the UI shows measured latency (queue + air + decode), not a theoretical figure.
7. **Devices are remembered:** selected audio/MIDI devices survive restarts and re-plugging (stored by name).
8. **Field gate** in `docs/release-checklist.md` passed, including 30 min without false Note Ons.

## Ordering rationale

TX scheduling and the watchdog live in the worker threads that move into `aml_engine`.
Fixing them in the GUI first would mean doing the work twice, so the order is:

**A. Core fixes → B. Extract engine (pure move) → C. Engine-level fixes → D. Thin shells + product polish**

## Phase B — Extract `aml_engine` (behavior unchanged)

New crate `aml_engine` (deps: `aml_core`, `cpal`, `midir`, `ringbuf`):

```
aml_engine/src/
  audio.rs      single copy (today duplicated in CLI and GUI)
  midi.rs       port listing and connection
  devices.rs    name-based device identifiers
  decoder.rs    RX worker (from aml_gui lib.rs)
  encoder.rs    TX worker (from aml_gui lib.rs)
  events.rs     EngineEvent
  lib.rs        public API
```

```rust
let dec = DecoderHandle::start(DecoderConfig { audio_in, midi_out, profile })?;
let enc = EncoderHandle::start(EncoderConfig { audio_out, midi_in, profile, simulate })?;
enc.send(TransportMessage::Panic);
for ev in dec.events().try_iter() { /* EngineEvent */ }
// Drop / .stop() shuts the worker down cleanly
```

`EngineEvent`: `Log`, `Level(f32)`, `Decoded(TransportMessage)`, `Stats(LinkStats)`, `Alarm(AlarmKind)`, `TxStatus { queued, latency_ms }`.

Audio and MIDI sit behind traits (`AudioSource`, `AudioSink`, `MidiSink`) so the full chain
(MIDI in → audio → MIDI out) can be tested without hardware and with a fake clock.

## Out of scope (deliberately)

UI framework change, FEC, MIDI channels, CC / pitch bend, full MSC SysEx.
All become easier after Phase B; MIDI channel is the cheapest next step but needs a protocol change.

## Open decisions

### Stuck notes after a lost NoteOff (A8)

Goal 2 cannot be met by the receiver alone: it cannot know a NoteOff was lost, and link-dead never fires while heartbeats arrive.
Options (both TX-side; C1 rebuilds the TX scheduler anyway):

1. **NoteOff refresh in idle slots (recommended).** TX keeps the ~32 most recently released notes for ~10 s and, in each idle heartbeat slot, sends a NoteOff for the oldest pending one instead of a Heartbeat (each note refreshed ~2×). No protocol or RX change, no extra airtime, still keeps the link alive, harmless if the note is already off, cannot overtake a later NoteOn (in-order TX).
2. **"Held notes" state message.** New message type listing currently held notes (paged); RX reconciles exactly. Stronger guarantee, but a protocol change.
